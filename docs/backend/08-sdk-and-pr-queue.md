# Launcher support, boot profiles and the PR drafter

## recomplauncher.json and the SDK

A developer can ship a `recomplauncher.json` in their release zips that tells the launcher how to start the game, where saves, settings and logs are, its setup step and its settings. The schema is published at recomplauncher.com/schema/recomplauncher.json (copied from the launcher's own `docs/recomplauncher.schema.json` by the 30-minute job). The developer guide and the AI agent guide are in `public_html/sdk-files/` (`guide.md`, `agent.php`, `examples/`).

To do: the agent guide is about 72,000 characters, and developers' AI tools stop reading at about 40,000. It needs splitting into short files (one per topic plus an index), ideally in the RecompLauncher-SDK repo, with the SDK page's buttons and prompts pointing there.

**Where the launcher reads it** (`profile::find` in the launcher): the `recomplauncher.json` inside the release it installed (top of the zip, or the AppImage root), then our profile from the catalog (the listing's `boot` field, carried as `launcher` when it's the json format). A file that's only in the developer's GitHub repo is never read by the launcher; it only helps once it's copied into their releases (or used as our profile).

**Setting up again** (launcher Beta 49): a finished setup only counts as not done when the player's files change, or when `prepare.version` changes (a developer changes it when everyone's copy has to be made again; in the SDK guide's Level 3). Launcher updates and other edits to the json never ask players to set up again. Installing a new release of a recomp still clears it, so a setup step runs again after each update. `prepare.done` (in the schema since 4.11; read by the launcher from Beta 51) lists files that exist once the step has finished, so a build the player made with the developer's own launcher counts as done.

**Easy Setup** (`rs_sdk_easy` in PHP, `sdk_easy` in draft.py): a game has it when its json has a `start` and a `game` entry, or a required input with role `game` or `disc`. That means the launcher asks the player for their own copy once and passes it along, straight to the game (a `--rompath` style flag) or to the setup step first. The launcher uses the same rule for its badge.

## Launcher support page (`admin/sdk-support.php`, data in `inc/sdk.php`)

Was "SDK support". Tabs:
- **Games**: every listed recomp with a repo, whether it ships its own `recomplauncher.json` (and the README badge), and marks set by hand: pull request open (`pr`), developer won't support it (`no`), PRs closed. The 30-minute job looks for the file in recomps not checked this week, most downloaded first. A file found in the repo or the release counts as shipping it whoever added it, whatever the pull request mark says. When a pull request is seen merged or closed (`rs_sdk_pr_state`), that game's check is cleared so the next run looks again.
- Games rows the PR queue is working on show its stage (**In the PR queue**: waiting, drafting, draft ready, going out) instead of No file yet; a sent one counts as a pull request open. **Developer replied** (orange) when a developer answered and nobody has since.
- **PR queue** (`inc/sdk-queue-tab.php`): seven stages with counts (**Developer replied** added in 4.12: `rs_prq_reply_scan` in `inc/prq.php`, from the 30-minute job through `rs_prq_send_due`, reads each sent or hand-marked pull request's (or issue's) comments, reviews and review comments; the newest one by someone outside the team (`prq_team_logins`, default elripalda,xarishark, plus our PR account; bots never count) newer than ours puts it there while the pull request or issue is still open; one of us answering on GitHub, or **Mark answered**, puts it back in Sent). **Send green drafts by themselves** (owner, Settings; `prq_auto_green`, on by default): a draft the review marks green (level ok, no blockers, new drafter, no code edits, not a redraft of a sent one) goes to Going out when it arrives (`rs_prq_auto_line` from `rs_prq_draft_save`, and `rs_prq_auto_sweep` each run for ones already waiting). Then:, each its own view (`?tab=queue&show=`): waiting to be drafted (`todo`, with why one didn't draft and what to do), drafting now, ready for you (`draft`), going out (`outbox`), sent, skipped (with **Put it back**, `prq_unskip`). Each draft has a review (`rs_prq_review` in `inc/prq.php`): what it gives players feature by feature, warnings (no Easy Setup, made by the old drafter, code changes nobody built, notes to read) and blockers (not JSON, fails the launcher's schema, no `start`). Send stays off until **I've looked it over** is ticked, asks once more listing what's in it, and the server refuses it without the tick or with a blocker. Drafts made before the 4.11 drafter (no `found.v`) are marked old; **Make new drafts for the old ones** (`prq_redo_old`) redoes them. Owner settings (token, keys) are at the bottom.
- **Guide** (`inc/sdk-guide-tab.php`): how the section works, every stage and button, what to do when something goes wrong, what's automatic and what it costs. Keep it in step when the queue changes.
- **Check a game** (`inc/sdk-check-tab.php`, checks in `inc/sdkcheck.php`): one recomp, what players really get, and test drafts.
  - `rs_sdk_health($a)` (kept 6 hours, **Check again** redoes it): which file the launcher uses (the developer's from their release, our profile, our older profile, or nothing), each file checked against the launcher's schema (`rs_json_schema_errors`, a small draft-07 checker for the rules the schema uses), the paths in it checked against the release zip's file list, and feature by feature (installs and updates, the program it starts, Easy Setup, setup step, settings, saves, logs, checking the player's copy, whether the file reaches players, the badge) with a fix for each. Plus player reports and logs of the last 60 days.
  - **Test drafts** (`rs_prq_dry_*` in `inc/prq.php`): the drafter run on this one recomp with the models ticked (Haiku, Sonnet, Opus, or Haiku reading and Sonnet writing code), side by side. They're written to `recompstore-private/prq/dry/<id>__<model>__<time>.json`, never saved to the queue or sent; each shows what it cost (its tokens at the AI usage prices) and goes on AI usage. A finished one can be **Put in the PR queue**, **Use as our profile** (`rs_prq_use_here`: players get it with the next catalog update, without the developer; code changes can't come this way), or sent to the developer (hub message, email or an issue with the file in it).
- **Look up a repo** (`?tab=lookup`, linked from Check a game): one that isn't listed yet.
- Check a game opens with **Next step**: where the game is in the queue (or that the developer ships their own file, or said no) and the button for it. The Games tab's side panel opens it with **Open its page**.

## Boot profiles (`inc/boot.php`, page `admin/boot.php`)

How RecompLauncher starts a recomp, does Easy Setup from the player's copy, and which settings it shows. They used to live inside the launcher (263 of them); now each listing's `boot` field holds its profile and the catalog carries it. The launcher's own copy is only used when the catalog can't be read. A developer's own `recomplauncher.json` wins over our profile.

## The PR queue (`inc/prq.php`, `api/prq.php`, `tools/prq/draft.py`)

Pull requests that add RecompLauncher support (recomplauncher.json and the README badge) to recomps that don't have it.

1. **Picks**: `api/prq.php` hands out the next ones: anything queued by hand first, then half newest recomps, half most downloaded console ports, all with no file yet.
2. **Drafting**: `draft.py` reads the project (README, up to 900 of its file paths, the newest releases, the file names inside the Windows zip read from the zip's index with ranged requests, the files that look like they handle the command line and paths, up to 4 docs or sample configs about its settings or command line such as `docs/CONFIG.md`, and up to 5 release/packaging scripts), drafts the json and a report with Claude (the model set for the PR drafter on Settings > AI usage, Sonnet by default; `PRQ_MODEL` still overrides it; it stops when the day's AI budget is used up, and each project's token use is sent back with the draft and counted), checks the json against the schema, and posts the draft back. The aim is the PR a person would send by hand: Easy Setup from the player's copy, a setup step that builds or imports the game when it needs one (with `start` on the game it makes, never on the builder), settings, saves, logs, and the file shipped in the release.
   - **Models**: the reading step uses the model set for "PR drafter: reading the project" on AI usage, the code step the one for "PR drafter: code changes" (`PRQ_MODEL` and `PRQ_MODEL_CODE` override them). Token use is sent back per model.
     Set to Haiku reading and Sonnet coding after the Nov 14, 2026 test runs (5 projects, each model, $12.50 in all). Average cost a project: Haiku alone $0.06, Haiku + Sonnet $0.34, Sonnet $0.53, Opus $1.12. Haiku alone only manages the release copy line, never a `--game` or `--prepare`; Haiku + Sonnet added the setup step where it fit as often as Opus (Skate 3, Ghostship, FEFW), with code that uses the project's own functions. Opus is there for hard ones in Check a game.
   - The code step retries when its answer is cut off at the length limit (it used to drop the code quietly), and when it leaves out a todo item without saying why.
   - **Test runs** (`PRQ_DRY=<folder>`): picks come from `api/prq.php?a=todo&ids=…&dry=1` (the queue isn't touched), each draft is written to the folder instead of posted, and the cost goes to `?a=usage`.
   - It runs daily from the GitHub Action (`.github/workflows/pr-drafts.yml` on main, 7:23 am Phoenix, which checks out `tools/prq` from the `mac-support` branch so both drafters always run the same file) and on the server when someone asks for drafts on SDK support (`rs_prq_run` starts `recompstore-private/prq/draft.py`, three at a time, log in `run.log`).
   - **Code step** (`code_todo`): runs when something is missing, and asks only for that. When the only thing missing is the release copy line, it reads just the packaging scripts, and makes no model call at all when the release is only made by a workflow (it says which workflow should copy the file). The rest: `game` (no way to receive the player's copy: use an existing option, or add `--game <path>`), `prepare` (the project has a setup or build step and the json has no `prepare`: add a `--prepare` mode or subcommand that does it without a window, calling the function its own screen calls, printing `progress <0-1> <text>`), `packaging` (the release zip has no `recomplauncher.json`: one copy line in the release or packaging script; never a `.github/workflows` file, since the PR token can't push those, so it says which step should copy it instead). It may ask once for up to 6 more files from the tree to follow the path to the function that does the work. Edits are find/replace on files it read whole, each with a `why` used as its commit message on Send.
   - **Found**: the draft carries what the project already has, feature by feature (`found.features`: `what` (always Game location, Setup or build step, Saves, Start straight into the game, Fullscreen or borderless, Settings file, Logs, Mods or packs, Release packaging), `has`, `how`, `where` as file:line, `used` by the json, `hook` (the launcher can drive it: a flag, environment variable, settings key or fixed path, including places the setup makes inside the install folder; a feature only in the game's own menus has none and gets no tick), `added` by this PR, `why` the json doesn't use one it has, and for missing ones `needed` and `why`), plus every command-line option it reads.
   - GitHub's API limit is shared across the account's tokens; `gh_room()` waits for it to reset.
3. **Review** on SDK support: each draft shows its newest release's files (the ones the launcher downloads per system marked), the Features cards (a tick only when the json uses it or the PR adds it) with what the PR does with each ("Feature added with this PR", "Flag exists, added to json", "Flag exists, not in json", "In-game only, nothing to pair with the json", "Not needed", "Missing, not in this PR"), the options list, the json and the PR text. Edit, **Send** or skip. **Draft them all again** redrafts the whole queue.
4. **Send** forks the repo with the saved GitHub token, commits the json and the badge on a branch, and opens the PR. At most 5 go out an hour; the rest wait in line (30-minute job). PRs that later conflict are rebuilt on the developer's newest code.

**After a pull request** (`rs_prq_sync_repo_files`, every 30 minutes from `pc-refresh.php`): for every game we sent a pull request to (queue rows `sent`, or marked "pull request open"), and any game whose check found the file in its repo (many developers close our pull request and commit the file themselves), the developer's `recomplauncher.json` in their repo is read every 6 hours. When it differs from our profile and passes the launcher's schema, our profile becomes their file and the game is republished, so their changes after merging reach players without anyone asking. It stops once their release ships the file (theirs wins), never replaces an older-style profile of ours, and keeps our copy (logged once) when their file fails the rules or starts a program that isn't in their current release download and has no setup step to build it (`rs_sdk_release_names` + `rs_sdk_program_in` in `sdkcheck.php`; a file ahead of its release, or a typo). State per game in `kv_cache` `prqsync:<id>`; Check a game's "The file reaches players" row says whether our copy matches theirs.

Rules for the PR text (in draft.py's prompt): plain and friendly, no mention of AI, tools or models, and it never claims the code was built or tested. A project that already has a RecompLauncher PR (ours or anyone's, open or closed) is skipped.

The PR body follows the hand-made ones: What it adds for players, Not in this pull request yet, The code changes, Things that would make your recomp better, For the developer, What's RecompLauncher?. The first two lists are worked out from the json itself, never from the model's claims: installs and updates, Easy Setup (with a setup step, through an existing option, an option added here, not needed, or missing), settings, saves, logs, exit codes, mods, the badge, and whether `recomplauncher.json` reaches the release.

## A submission's file before it's approved

`sdk-support.php?tab=check&sub=<inbox id>` (linked from the Submissions drawer) runs test drafts for a PC submission on GitHub that isn't a listing yet. `rs_prq_sub_pick` turns the submission into a pick with id `sub-<id>` (`unlisted`, so the PR text doesn't link a page). Its runs are files like any test run (`sub-<id>__model__time.json`): copy or download the json there. Once Auto-add has made its listing (`rs_prq_sub_app`, from `pc_auto.sub_id`), the runs also show on the listing's Check page, where "Use as our profile" and "Put in the PR queue" work (`rs_prq_dry_to_queue` moves a `sub-` draft to the listing's id).

## Replies (4.13)

`inc/sdk-replies-tab.php`, `?tab=replies`. Every pull request and issue we sent (`pc_prq` rows sent in the last 180 days) and the ones marked by hand (`sdk_marks`), with the developer's answers, open or closed.

- **Tables** (`rs_prq_reply_tables` in `inc/prq.php`): `pc_prq_threads` (one per game: url, repo, kind `pull`/`issues`, number, title, state `open`/`merged`/`closed`, `closed_at`, `theirs_at` their newest comment or review, `news_at` their newest anything including a merge or close, `ours_at` our newest comment, `read_at` Got it, `checked`) and `pc_prq_msgs` (each comment, review, code comment, the opening post and who merged or closed it; `mine` when the login is on the team).
- **Reading** (`rs_prq_reply_scan`, from the 30-minute job through `rs_prq_send_due`, 50 seconds a run): open ones every hour, closed or merged ones every 6 hours for two weeks and daily up to 90 days, then left alone. Never-read ones go first. Reads use the PR account's token (`rs_prq_gh_read`), else the site's GitHub calls. **Check now** (`prq_reply_check`) starts `inc/prq-replies-run.php` in the background for every open one (once every 2 minutes at most).
- **New**: something of theirs after our last comment and after **Got it** (`rs_prq_reply_ok`, also the queue's Mark answered). A thread closed more than a week before it was first read starts as read. **Waiting on us**: open, and their last comment is newer than ours. That's what `rs_prq_replies()` gives the PR queue's Developer replied stage and the Games list.
- The tab's count in the menu is how many are new. Views: New, Waiting on us, Open, Merged or closed, All; each item shows their newest message, the whole conversation, Answer on GitHub, Got it and its page.
